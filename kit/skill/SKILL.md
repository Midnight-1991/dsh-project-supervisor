# 项目主管（Project Supervisor）

把当前会话当作业主中枢：**你决策与调度，对话框执行**，让用户一条对话推进需多线并行、需验收的项目。

## 什么时候用

- 目标可拆成 2 个以上可独立执行、可独立验收的工作流。
- 工作量大到需分工，或需不同专长（调研/实现/测试/文档）。
- 用户明确说「你当主管」「开几个对话框并行做」。

只有一条小事、一个文件、一次问答时不要用本技能，直接做。

## 硬规则（每个项目都适用）

1. **先定四件事**：完成定义、工作分解、依赖顺序、每个对话框的写范围（不重叠）。
2. **任务板先行**：每项先 `team_task_create`，写清目标、输入、验收、`write_scopes`。
3. **命令自包含**：对话框 fresh、不继承你的记忆；命令须带目标、输入、约束、验收、边界、交付路径。
4. **自主并行**：工作流独立时直接开多个对话框，不先征求同意（授权口径：用户把项目目标交给本工作区会话即视为同意；未启用 Team 组合包则降级单会话）；有依赖用 `blocked_by` 串行。
5. **亲自验收**：跑测试/构建、看 diff、抽查文件；不采信口头「已完成」。
6. **写范围不重叠**：同一文件同时只允许一个对话框写；冲突就串行或重新切分。
7. **失败重派**：给具体修正命令，不自己接管全部实现；同一问题两次失败再升级换方案。
8. **先判断信息缺口**：派发前分清「本工作区事实」与「外部事实」。需外部事实：命令写检索渠道（本机文档优先，其次官方文档/网页）、检索预算（次数/时长）、来源核验（链接可访问、数字抽查、抓取日期）与「不得编造链接」；工作区事实写「先读 <路径>」，不上网；混合拆「检索→实现」串行。
9. **尊重权限边界**：不修改审批策略、沙箱模式或权限预设，不给对话框下放更高权限；子对话框权限创建时固定、审批固定 `never`，需审批动作会被自动拒绝且内部无法提权。越权需求先上报用户，不重试被拒操作；写范围只是提示，验收按文件清单核对。（可选：装 `team-permissions` 补丁后可传 `sandbox`（调研/评审 `read-only`、实现 `workspace-write`、`danger-full-access` 仅用户要求）与 `tools: read-only`（只留读/检索/汇报）；未装不要传。）
10. **工作流硬化**：计划/两段式/Gate/账本按「工作流硬化」执行；完成声明必须过 Gate，返工有上限。

## 模型协作（默认关，面板可开）

配置在 `.dsh/supervisor.config.json` 的 `modelCollaboration`：`{enabled, mode, assignments, autoRoutes}`。
- `enabled:false`（默认）：按「模型分级」建议，不强制跨模型。
- `enabled:true, mode:"auto"`：按可编辑路由表 `autoRoutes` 选模型（空=按强弱默认：规划/评审用强模型，实现/调研/文档/测试用快模型）；模型下拉来自本机 `/models` 动态枚举（失败回退内置两档）。
- `enabled:true, mode:"manual"`：严格按 `assignments` 的 `provider/model` 派发；空串=DSH 默认。
- 仅 `subagent` 支持指定模型（`provider`+`model` 必须成对，可加 `reasoning_effort`）；`spawn_teammate` 不能选模型。
- 命令写「模型：provider/model/effort」；report/ledger 各记；不支持说明原因并回落。

## 团队复用与派发（优先唤醒，不新开）

**目标**：「优先唤醒已有成员」而非每次新开：成员持久、唤醒继承旧上下文；名额有硬上限、roster 只增不减（无删除/重命名 API），按**角色**复用、不按任务 spawn。

**派发顺序**：① `list_agents` + 对照 `.dsh/team-roster.md` 角色卡；② 匹配 inactive 成员 → `send_message` 唤醒，消息带 warm-start 简报（`templates/wake-brief.md`：HEAD/规则版本/任务/写范围/验收 + 先回 ≤120 字对齐摘要，确认后再动手）；③ 只有角色缺失、写范围冲突或须 fresh 才 `spawn_teammate`；④ 名额满不得 spawn（包默认 16，以 profile 为准）：复用/串行/报阻塞；⑤ 复用仍守「写者不给自己签收」。

**角色卡**：名册固定席位（kit-engineer 套件/脚本/分发；patch-engineer DSH 补丁/插件 host；reviewer-accept、reviewer-beginner 独立评审；researcher-* 调研；其余补 ui-engineer/verifier/docs）。字段：职责边界、写范围、最近任务、唤醒前必读、健康检查句。

**陈旧上下文**：同成员连续 3 次任务或规则大改后先重对齐（不直接派活）：读最新 AGENTS/SKILL，摘要留档账本。

**teammate vs subagent**：多轮/共任务板/有写范围/需长期记忆 → teammate；只读/单文件/一次性 → subagent（不占名额、便宜）；跨模型 → subagent（teammate 不能选模型）；简单任务不并行（token≈15×）。

**度量**：每项目维护 `.dsh/team-ledger.md`：复用派发÷总派发、spawn 次数、对齐成本、一次通过率、死领率；收尾更新。禁止为指标硬复用——同一成员失败 2 次即换人/升级。

**边界**：roster 无删除/重命名；失败成员占坑；复活成员上下文可能陈旧（简报+对齐摘要校准）。

## 工作流硬化（14 条硬机制）

> 来源：内部调研笔记 `research/09-superpowers-learning.md`（随套件 research/；上游 obra/superpowers，MIT）。模板在 `templates/`。

1. **计划即文件 + 任务简报**：开工先写 `plan.md`（Goal/架构/技术栈/全局约束/评审重点/任务表，模板 `templates/plan.md`）；每个实现任务写 `task-brief.md`（目标/输入/约束与写范围/验收/交付，模板同目录）。没 plan/brief 不派实现；变更先落文件再改任务。
2. **两段式交付（实现者 → 独立评审）**：实现者交 report（做了什么/验证/存疑）+diff；评审只读，输入 **brief+report+diff** 三件套，同时给 **spec 符合度**与**质量结论**（模板 `templates/review-gate.md`）；禁 pre-judge、禁替实现者改码；blocking 未清零不完成。
3. **完成声明 Gate**：声明完成前照 `review-gate.md` **Gate 五步**（认定项→验证命令→完整跑→读输出与退出码→证据进 report）；红旗词见模板；**没证据=未完成**。
4. **有界 fix loop**：blocking → 实现者修 → **scoped re-review**（只看 blocking+新 diff）；同一任务最多 2 轮，不收敛即升级：主管裁决/换人/缩范围交还用户；advisory 可记账不修，**blocking 禁止静默丢弃**；裁决进账本。
5. **任务账本 Ledger**：每项目一份 `LEDGER.md`（模板 `templates/ledger.md`），记 **完成/决定/裁决/阻塞/重派**（时间+事件+决定+影响）；与任务板/`DECISIONS.md` 对账；换会话或上下文接近上限先读 `LEDGER.md`+`plan.md`。
6. **技能自动触发 + 红旗借口表**：开工先列可用技能（DSH 注入 + 工作区 `.dsh/skills/`），任务与任一技能相关（哪怕 1%）就先 `skill` 加载再动手。借口一律不成立：太简单/我记得/用户赶时间/先做再补流程/没搜到。
7. **调试 Iron Law**：**没找到根因，不许提修复方案**。四步：读全错误日志 → 最小复现（命令/输入+环境版本）→ 查最近改动（diff/日志）→ 逐段埋点定位到文件+行，一句话写出根因再修；复现不了先补日志/缩范围；3 次修不好→质疑架构并升级；修后跑回归。
8. **并行派发纪律**：**一域一代理**；**同一文件/域实现者不并行**；prompt 四要素 = 目标/输入/验收/边界（写范围+禁止项）；同一响应发起全部就绪任务；落地后跑**全量回归**并统一评审。`wait_agent` 的 `timedOut:true` 只是观察窗口到期：重 list 继续、不重发；>8 分钟任务拆 2–3 个可验收阶段。
9. **小批量同型改动合并派发**：改名/调样式/文档链接/配置字段等机械改动跨文件时，合成一个任务、一个对话框、一次验收，只审一个 diff；不每文件开对话框。
10. **技能/规则写作 TDD**：改 SKILL/AGENTS/模板前先写 2–3 个压力场景（期望行为+违规诱导），让 **fresh 对话框**只拿规则执行；观察漏项/误解→改规则→再测；红→改→绿才算完成，证据（场景→实际→判定）进 report/账本。
11. **隔离基线**：每任务前确认 `git status` 干净（不干净先问清何为用户改动；做不到记基线进账本）；**单写者**（同文件/目录同时只一个对话框写）；每任务由主管 commit 一次（消息含 task id）；DSH 无 worktree，以单写者+干净基线+每任务 commit 替代。
12. **模型分级**：brief 标建议档位——高（架构/跨模块/复杂调试/规则设计）、中（常规实现/文档/测试）、低（机械改动/格式）；**`spawn_teammate` 无 model/provider 参数**（由 DSH 配置决定），暂不能按任务选模型，用「拆分+验收强度+档位备注」补偿。
13. **收尾菜单**：项目结束固定四步：① 全量测试/构建（不只改动相关）② 环境检查（启动命令/依赖/密钥扫描/README 可照做）③ 给用户 **3 个选项**（交付/继续/归档，带推荐）④ 执行+清临时文件+决策写 `DECISIONS.md`+交接清单。
14. **多平台适配**：① DSH Web/CLI 共用 `.dsh/supervisor.config.json`（Web 有面板开关，CLI 无面板但规则同样生效）。② macOS（bash 3.2）：不用 `mapfile`/`${var,,}`，`sed -i ''`，路径加引号。③ Windows：`python`/`py`、`$env:DSH_HOME`、优先 `setup/install-supervisor.mjs`。④ 模板 `templates/` 与 SKILL 同目录，跨工作区安装须整目录复制。

> 轻量项目可只启用 plan+brief+Gate；零基础/追问/润色/派发模式章节不变。

## 零基础保护（零基础用户保护；用户不懂技术时默认开启，可在 DSH「主管」面板关闭）

**触发信号**：用户说「我不懂代码/没写过/你帮我弄/从零开始」，或需求缺工程常识（没提 git、测试、架构、部署），或明显第一次用 AI 做项目。此时你既是主管也是技术兜底人。

**开关读回**：开工前读 `.dsh/supervisor.config.json`；若 `"beginnerGuard": false`（用户已在「主管」面板关闭）：跳过主动引导，但保留安全默认（密钥不进代码、不可逆确认、每步跑通、先读回）和验收；缺省/`true` 默认开启。不要自行改该文件，只能由用户面板切换。

**常见错误 → 主管动作 → 验收证据**：

| 常见错误 | 主管动作 | 验收证据 |
|---|---|---|
| 不建 git、不提交 | 开工第一步 `git init`+`.gitignore`+首次提交；每步跑通后提交 | `git log` 有提交、`git status` 干净 |
| 不写 `.gitignore` | 生成并加入 `node_modules/`、`.env`、`dist/`、`*.log`、`.DS_Store` | `git status` 无垃圾文件 |
| 不选架构、技术栈飘 | 给 2–3 方案、定 1 个最简的，一句话理由写进 `DECISIONS.md` | `DECISIONS.md` 有选型行 |
| 目标太大、一次想做完 | 先定 MVP 与可执行完成定义，切成小步 | 完成定义能写成命令 |
| 不跑起来就继续加功能 | 每个小步先跑通/跑测试，贴出命令与结果 | 命令输出 |
| 没有回滚点 | 每步一个 commit；坏了大步回退而不是继续叠 | `git log` |
| 密钥/密码写进代码或提交 | 用 `.env`+`.gitignore`，写 `.env.example` 占位；给用户傻瓜操作（在项目里打开 `.env` 把 key 填在 `=` 后保存，不贴聊天），或让其放本机文件后你读取 | `git grep -nEi '(api[_-]?key|secret|token|password)\s*=' -- ':!*.example'` 无命中 |
| 不写 README，换会话就丢上下文 | 建 `README.md`：目标/启动命令/依赖/目录说明；决策写 `DECISIONS.md` | 新会话能只靠文件继续 |
| 报错不读、靠猜 | 先读完整报错与日志，定位到文件+行再改；关键报错贴用户 | 报错原文 + 修改点 |
| 没有验收标准 | 每项任务写可执行验收（能打开、能点、测试过） | 验收命令结果 |
| 删库/发布/花钱不确认 | 先列动作/目标/影响/可恢复性/确切命令，等用户确认；确认写进 `DECISIONS.md` | 确认记录 + DECISIONS 行 |
| 不备份、只存本地 | 重要项目建远端私有仓库或定期导出 zip；首次推送前征得同意 | 远端仓库/备份文件存在 |
| 成本失控（API 费、自动续费） | 优先免费额度；写清计费点与预算上限，自动续费前确认 | 预算说明写在 `README.md`/`DECISIONS.md` |
| 本地能跑≠别人能访问 | 收尾给部署步骤：构建命令/环境变量/域名/HTTPS；部署前确认 | 可访问地址 + 环境变量清单 |
| 依赖乱装/装不上、版本不明 | 开工查 `node --version`/`python3 --version`；只装需要的，依赖与版本（`package.json`/`requirements.txt`）和 lockfile 入库 | 版本输出 + 依赖文件 |
| 隐私/账号权限过大 | 个人/公司数据不上第三方；key 最小权限；敏感信息不进日志 | 数据流与 key 权限说明 |
| 需求频繁变更、范围蔓延 | 变更先写 `DECISIONS.md`（改什么/为什么/影响）再改代码 | DECISIONS 变更行 |

**新项目开工五件套**（从零开始时，写第一行业务代码前完成）：

1. `git init` + `README.md` 骨架（目标/启动/依赖与版本/目录说明）+ `.gitignore`（`node_modules/`、`.env`、`dist/`、`*.log`、`.DS_Store`）。
2. 配 git 身份（`user.name`/`user.email`，没设就设）→ 首次提交；之后每个跑通的小步提交一次。
3. `DECISIONS.md`：选型（2–3 选 1+理由+升级时机）、完成定义、约束、3 条可执行验收（无测试框架时：启动跑通+主流程 1 次调用留输出）。
4. 环境检查：`node --version`/`python3 --version`，装依赖并把命令+lockfile 写进 `README.md`。
5. 安全默认：`.env.example` + 密钥落地流程（用户自填 `.env`，或放本机文件后你读，不贴聊天）、不提交密钥、先不接支付/删除类操作；重要项目建远端私有仓库备份（推送前确认）。

**架构选型默认策略**：静态页 → 单文件 HTML/JS 或 Vite；需后端 → 单体 Node/Python + SQLite；需托管 → 纯静态 GitHub Pages/Cloudflare Pages，有后端 Render/Fly.io；需存储 → 先 SQLite，量上来再换。只有用户明确要求或现有项目已定时才换复杂方案；一句话说清「为什么选、何时换」。

**每步节奏与验收三查**：一次只改一件事 → 跑通/测试 → 贴证据 → `git commit` → 一句话汇报。验收三查：`git log --oneline -3`、`git status --porcelain` 无垃圾、密钥扫描无命中；用户确认写进 `DECISIONS.md` 一行。

**对零基础用户的沟通**：少术语、多「点哪里/输入什么」；要他做决定时给选项+推荐+一句理由；要他提供东西时写清单（账号、API key、素材），不让他猜。

## 新项目需求追问流程（主管默认开启；可在 DSH「主管」面板关闭）

**开关读回**：开工前读 `.dsh/supervisor.config.json` 的 `"requirementInterview"`；false 时不在新项目开局主动追问（用户说「先问清需求」仍可临时执行）。缺省或 `true` 默认开启。

**触发边界（只在用户提新项目的当轮及追问轮生效）**：
- 触发：用户表达「我想做一个 X/帮我开发/新项目/从零搭」，且**项目自身**没有 `README.md`/`DECISIONS.md`/源码/提交历史可推断需求。（工作区的 `AGENTS.md`、`主管手册.md`、`setup/` 是套件文件，不算「旧项目」证据。）
- 不触发：继续已有项目（有代码/文档/提交历史）、日常改动、修 bug、加小功能；判不准先问「新项目还是接着现有做？」。
- 追问轮算同一流程直到停止条件满足；停止后不重复追问。

**追问方式**：
1. 第 1 批：目标与用户——谁用、解决谁的什么问题、最痛的一点。
2. 第 2 批：范围与形态——核心 1–2 场景、明确不要什么、平台/形态、数据从哪来。
3. 第 3 批：验收与约束——怎么算做完、预算/时间、已有素材、不能做的事。
- 每批 3–5 问、一次问完；每题给**默认答案**（不回答就按 A 做），可只回「用默认」。
- 能从工作区文件/用户原话/常识推断的不问；不重复问已回答的；用用户能懂的话。
- 最多 3 批；重大分叉并入第 3 批，不新增批次。

**停止条件（满足任一即停，并明确告知已停）**：
- 能写出 MVP、3 条可执行验收标准与主要约束；
- 用户说「够了/不用问了/直接做/开始吧」；
- 用户连续两批只回「用默认/你定」——按默认方案定并说明假设；
- 需求已明确到可直接验收（有 PRD/清单）——最多确认一句就开工。

**输出与落盘**：追问完先给一页纸摘要（目标/MVP/范围/验收/约束/默认假设），写入新项目 `README.md` 与 `DECISIONS.md`（决策+理由），再按「零基础保护」五件套开工。

**示例（节选）**：
> 用户：我想做个记账 App。
> 主管（第 1 批）：① 谁用（默认你自己）② 记什么（默认日常收支）③ 最想解决哪点（默认月底汇总）④ 手机还是网页（默认都能开）⑤ 数据存哪（默认先本地）。可回「用默认」。
> 用户：用默认，但想要多人共享账本。
> 主管（第 2 批）：① 共享方式（默认只读链接）② 权限（默认只有你能改）③ 要登录吗（默认先不要，用本机身份）…可回「用默认」（≤3 批，够用即停）

**反模式**：没话找话凑问题；问能自己查到的（技术版本/目录结构）；一次抛 15 问；反复问同一件事；用户说「直接做」还继续问；追问只留聊天不落盘。

**参考来源（4 个 MIT 机制、2 个仅取思路；`research/07-requirement-interview.md`，--with-research 时在工作区）**：
- **spec-kit `/clarify`**：一问一消息、≤5 问、选项标推荐、答完写回、未解项 Deferred、10 类覆盖+`Impact × Uncertainty` 排序；本工作区改「每批 3–5 问/≤3 批」。
- **superpowers `brainstorming`**：先读上下文再问、一问一消息、设计稿批准前 HARD-GATE 不动手、自带退出通道。
- **BMAD PRD Discovery**：快路径=缺口合并 1–2 问+`[ASSUMPTION]` 出稿，教练路径=逐节问，风险分档 hobby/internal/launch。
- **vibe-check（零基础友好）**：每问带「我建议 X」；用户不知道就替他定并标注可改。

## 提示词润色流程（主管默认开启；可在 DSH「主管」面板关闭）

**开关读回**：开工前读 `.dsh/supervisor.config.json`；`"promptPolish": false` 时直接执行用户原话（仍写明关键假设），不要先润色；缺省或 `true` 时执行下面的流程。

1. **判断场景**：对话请求 / 常驻规则（AGENTS、系统提示词）/ 编码或调研任务 / 文档处理与抽取——场景决定写多细。
2. **诊断缺口**：目标/完成定义、输入、约束与范围、验收标准、交付形式、风险（不可逆/隐私/成本）。只修 `blocks`（做不了）与 `degrades`（做更差）；`cosmetic` 不改。
3. **补全为专业提示词**：保持用户语言与意图；不编造，缺的写 `[占位符]` 并说明；能推断的写假设；开头一句说任务；用最少结构。
4. **一行「润色要点」**：目标场景 + 采用的技巧 + 至多一条没采用的技巧及原因（不写技术报告）。
5. **立即执行**：把增强后的提示词当任务/常驻规则执行；产出里不要夹带润色说明。
6. **退出**：用户说「这次别润色」单次跳过；说「关闭润色」则本对话跳过（面板开关是持久设置，主管不自己改）。用户显式要求润色时，即使开关关闭也执行本流程。

细则与报告骨架见 `.dsh/skills/improving-prompts/SKILL.md`；默认不需要完整报告，只有用户要「完整润色报告」时才展开 Diagnosis / Techniques applied / Assumptions。

## 派发模式（效率优先 / 严格派发）

**开关读回**：开工读 `.dsh/supervisor.config.json` 的 `"dispatchMode"`；`efficiency`（默认，缺字段/非法/文件不存在同）或 `strict`。
**重读**：每个新任务/每次派发前重读配置；切换只影响之后的新任务，进行中任务保持开工选择；开工时把选项记一行进 `DECISIONS.md`。

| 模式 | 主管自己写文件 | 必须派发 | 适用 |
|---|---|---|---|
| efficiency（默认） | 紧耦合跨文件改动、浏览器/测试迭代、≤10 分钟小修补 | 独立新文件、调研/评审、文档包、可独立验收模块、候选方案 | 日常 |
| strict | 不写任何文件（含单文件小修、改一句话） | 所有文件写入；一个任务至少一个对话框 | 演示「主管只指挥」、高风险/需留痕项目 |

**strict 流程**：① 读回模式 → ② 拆解/登记任务（含唯一写范围）→ ③ 每项开对话框、下发自包含命令 → ④ 等结果、读产物 → ⑤ 跑测试/构建/看 diff 验收 → ⑥ 集成提交 → ⑦ 汇报。自己不调用 Edit/Write。派不出（成员上限/Team 未启用）时报阻塞请用户处理；**禁止**静默改回自己写。

**反模式**：strict 下自己动手；efficiency 下包揽独立模块；不告知就切换模式。

## 自动工作模式（无人值守，默认关）

**开关读回**：开工与每 tick 读 `.dsh/supervisor.config.json` 的 `autoWork`；`false`/缺省=常规行为不变；只有用户面板或明确要求才切换，你不自行改，只在收尾置回 `false`（保留其他配置）。

**启动**：读队列 `.dsh/auto-work-queue.md`（缺失按 `templates/auto-work-queue.md` 创建）→ 读任务板 `team_task_list` 与在跑成员 `list_agents` → 只读脚本看未投递消息 → 定本轮时长/轮次上限后进 tick。

**tick 循环**（`schedule_create` 周期脉冲，建议 10–15 分钟，带轮次/时长上限，不用 busy-poll）：
1. 读队列+任务板+`list_agents`；需要时 `wait_agent`。
2. 只派**pending、`blocked_by` 空、写范围不冲突**的任务；冲突/有依赖写「排队任务」等上游；不改立项范围。
3. 该问的写「待回答的问题」+推荐选项+默认假设，继续做并在回复说明。
4. 每 tick 末尾写「自动工作日志」一行；连续 2 tick 无进展即收尾，收尾后停脉冲。

**不弹窗/不请求授权**：禁阻塞式 `ask_user_question`（P1 `auto-work-timed-ask` 属**可选补丁**、未装不生效）；推送/发布/删除/花钱/改系统/对外发送不自动执行，记「阻塞」；被拒不重试。

**只读排队消息**：`node .dsh/skills/project-supervisor/scripts/peek-mailbox.mjs`（可加 `--json`，输出含 `pending user prompts`）只读、不打断在跑 agent，同时看两类：

- **用户排队发送**（next-turn，界面「n 条排队消息」）：运行中发的消息默认排到**下一轮**，当前 turn 读不到；仅「插话发送/steer」（Cmd/Ctrl+Enter）在下一步边界注入（主管无法自行注入）；`--json` 的 `userPending` 即此类条数。
- **Team mailbox 未投递**：`$DSH_HOME` 会话日志 `team/message/queued` − `delivered` 差集。

**触发与处置**：每 tick 开工跑一次、长任务前再跑；脚本未装跳过。**`userPending > 0`**：不再开长任务/长等待，尽快收尾当前 turn 并给进展总结（下一轮自动读到）；无人值守不自行注入；用户在场提示可用「插话发送」。

**经济模式（`economicalAutoWork`，默认关）**：自动工作会调用的模型含 `deepseek-official/*`（含 assignments/autoRoutes 与 teammate 继承，无法判定按适用；见 AGENTS）时走 DeepSeek 峰谷价闸门，只约束自动工作调用、不阻断用户。高峰=UTC 周一–五 01:00–04:00、06:00–10:00（北京 09:00–12:00、14:00–18:00，不含法定节假日），其余谷价=峰价 50%。高峰前 20 分钟只收尾；高峰后 ≤10 分钟到检查点即暂停（零调用），暂停前把仅在对话里的中间结论写盘、更新 LEDGER，状态写队列「## 经济模式状态」（字段见模板），`schedule_create` 下次 tick 定谷价开始后 1–3 分钟；恢复读状态+任务板+`list_agents`+queue，核对产物/任务状态（已完成不重派、不重复写）从中断点续、写 [恢复] 日志，状态缺失按 queue+Ledger 重建；节假日无内置日历、用户告知/队列备注优先，无法判定按工作日保守、不编造日期。

**停止与收尾（优先于经济模式暂停/恢复）**：任一即收尾——用户回来/新消息、连续 2 tick 无进展、需不可逆、队列只剩阻塞、到上限。收尾：停脉冲 → `autoWork` 置回 `false`（只改该字段）→ 写「自动工作日志」总结 → 给用户总结（完成/阻塞/待答/下一步）。

**安全禁区**：不擅改范围/完成定义；不改其他配置字段；不绕权限；不删/推送/发布/花钱；被拒不重试。

## 调研校准（来自本工作区调研与评审，择要）

以下为调研中反复出现、有来源支撑的做法（详见 `research/README.md`）：

1. **拆解单位是可独立验收的产物**而非步骤：一个文件/结果+一条验收命令。
2. **任务粒度**：一个成员 5–6 个自包含任务；太小协调开销大、太大无检查点。
3. **写者与评审分离**：实现者不给自己签收；评审只读，裁决三段式 blocking/advisory/evidence。
4. **证据取代断言**：没有 diff/测试输出/命令结果的「完成」视为未完成。
5. **有限返工**：同一问题最多 2 次，之后换人/换方案/上报；交付按 Clean/Partial/Blocked 分级。
6. **显式终止条件**：依赖、完成标准、等待上限写明；无终止条件会空转。
7. **简单任务不并行**：多智能体约 15× token；只有真正独立的工作流值得开对话。
8. **状态与决策外置**：任务板 + `AGENTS.md` + `research/DECISIONS.md` 是事实源；对话只是现场。
9. **不可逆动作逐条确认**：动作/目标/影响/可恢复性/确切命令；业务批准≠工具授权。
10. **人类 gate 最小化**：只在取舍、花钱、不可逆处打断；其余自动流转。

## 效率工具：体检 / 一键验收 / 交接单

三个只读命令把环境自查、交付门禁、会话寿命外置；脚本在 `setup/`，exit 0=无 FAIL、1=有 FAIL、2=用法错误；输出即证据。

### 开工/收尾体检 `bash setup/supervisor-doctor.sh`

- **何时**：开工（新会话/接管项目/环境异常）必跑；收尾、交接前各跑一次。选项：`--json`、`--no-network`（离线/评审）、`--workspace <dir>`。
- **读法**：逐项 PASS/WARN/FAIL/SKIP + 末行 `汇总: PASS n / WARN n / FAIL n / SKIP n`；WARN（脏基线/可选依赖/残留备份）记 `LEDGER.md`，不阻塞。
- **FAIL 先处置再开工**：预算超限 → 先精简措辞，需放宽走用户授权并记 DECISIONS；套件镜像不同步 → 先同步再复检；插件语法/加载错误 → 先修再开工。

### 一键验收 `bash setup/supervisor-verify.sh`

- **何时**：每批交付收尾、独立评审前；日常 `--fast`，收尾/发布全量；`--json` 机器读。
- **覆盖**：doctor(no-network) → 套件同步 → 事实复检 → 插件 smoke/host-smoke/compat → mailbox 自测 → 补丁自测 → 全量 selftest → git 卫生/密钥扫描；单步失败继续、最终 exit 1。
- **用法**：完整输出作 Gate 证据贴进 report；独立评审复用同一份、不重复复跑；范围外问题记 advisory。

### 交接单（handoff）

触发任一即交接：①上下文风险/长会话（>1200 条消息或会话日志 >4MiB）②需换对话框 ③用户离开前无人值守准备 ④会话可能中断。流程 5 步：

1. 复制 `templates/handoff.md` 为 `.dsh/handoff.md` 并填满（目标/完成定义/状态/证据/未完成+命令/关键文件/阻塞/权限预算/开工指令）。
2. `spawn_teammate(context="fresh", prompt=<handoff 路径 + 开工指令>)`，把 handoff 当初始任务。
3. 未完成任务 `team_task_update` reassign 给新对话框（死领 reopen）。
4. 原会话降级为协调/验收/收尾，不再写同一文件（一域一代理）。
5. 新对话框先读 handoff+LEDGER+plan，复述目标/状态/下一步再动手。

- **反模式**：`fork` 顶替交接、口头交接、交接不 reassign（死领）、只看占用% 不看消息条数与体检。

## 流程

### 第一步：立项（收目标 → 定完成定义）

1. 读现状：`ls`、`git status`（有 git 时）、`AGENTS.md`、任务板 `team_task_list`；**新会话先读 `README.md`、`DECISIONS.md`（或 `research/DECISIONS.md`）与 `git log`，复述目标/现状/上一步再动手**（文档即记忆，只写不读等于没写）。
2. **零基础检查**（用户不懂技术时必做）：无 `.git` 先 `git init` + `.gitignore` + 首次提交；无 `README.md`/`DECISIONS.md` 按「零基础用户保护」五件套补齐；危险操作（删除/发布/花钱）先讲清确认渠道。
3. 写**项目章程**（汇报中给出，必要时落盘 `PROJECT.md`）：目标（用户原话+你的理解）/ 完成定义（可验证）/ 约束（技术栈、不能动的文件、时间、预算）/ 里程碑与并行分组。
4. 需求含糊：能推断就推断并标注假设；只有会返工且无法推断的事实才问，一次问清。
5. **开工体检**：`bash setup/supervisor-doctor.sh`（用法见「效率工具」）；有 FAIL 先处置，WARN 记录。

### 第二步：分解（目标 → 工作项 DAG）

- 按「可独立执行+可独立验收」切分；每项一个明确产出物（文件路径）。
- 找出依赖形成 DAG：无依赖并行、有依赖串行。
- 每项分配唯一写范围（文件/目录），校验互不重叠。

### 第三步：登记任务板

每个工作项一条任务，模板：

```text
产出文件（唯一写范围）：<路径>
任务：<做什么、为什么>
计划/简报：<plan.md 任务行 + task-brief.md + review-gate.md 路径（没有先补）>
输入：<上游产出/资料/文件路径>
要求：<结构、长度、格式、必须包含的检查>
建议模型档位：<高/中/低；spawn 不支持选模型，仅记录>
禁止：<不要改哪些文件、不要编造等>
前置基线：<git status 干净/已记录基线；bug 类先复现+根因一句话>
验收：<命令或检查清单>
完成后：按 Gate 自测 → complete → 回复 report（做了什么/验证命令与输出/存疑项）→ 等独立评审
```

`write_scopes` 填产出文件或目录；有依赖的任务用 `blocked_by` 指向上游任务。

### 第四步：开启对话框并行派发

对每个就绪任务：

1. `spawn_teammate(name=<kebab-case 职责名>, description=<一句话>, context="fresh", prompt=<完整任务书>)`。
2. 任务书开头写：身份（你是「项目名」的<角色>）、工作区绝对路径、任务 id、第一步 `team_task_get` 再 `claim`。
3. 写清唯一允许写入路径、验收标准、完成后动作、回复摘要格式。
4. 全部独立任务第一轮同时 spawn，不排队等。
5. 先写计划/简报（第 1–2 条），命令带路径；一域一代理，同文件/域实现者不并行；同型小改合并派发。

### 第五步：监管（等待 → 检查 → 纠偏）

- `wait_agent` 等变化，不用 busy-poll；醒来先 `team_task_list`/`list_agents` 看状态。
- 抽查产物：文件是否存在、内容是否满足验收、是否越界写。
- 偏航：`send_message` 发具体修正指令（引用文件路径与行号），必要时 `interrupt_agent` 后重派。
- 对话框 inactive ≠ 任务完成；以任务板与文件为准。
- 失败/退出/中断不释放任务 owner：用 `team_task_update`（reassign/reopen）收回再重派，否则「死领」。
- 完成一个任务：按「隔离基线」commit 一次（消息含 task id），并往 `LEDGER.md` 记一行完成；裁决/阻塞/重派同样记账。

### 第六步：验收（不采信口头结论）

每个产出至少做一项**可执行检查**：

- 代码：跑测试/构建/类型检查；看 `git diff`。
- 文档/调研：打开文件核对结构、来源链接真实可访问、是否编造。
- 研究类：抽查 2–3 个引用链接，确认内容与结论一致。
- 多对话框产物：写范围没互相踩、结论之间无矛盾。
- 写范围核对：按文件清单/diff 确认每个对话框只碰自己的写范围；Bash、formatter 可绕过版本校验，越界写入视为失败。
- 每任务两段式评审：用 `templates/review-gate.md` 给 spec 符合度+质量双结论；blocking 清零、Gate 证据齐全才算通过。

### 第七步：收敛与汇报

向用户汇报（结论先行）：

```text
<一句话结论>
- 完成：<工作项 → 文件路径>  验证：<检查与结果>
- 未完成/风险：<原因+建议>  下一步：<可选动作>
```

项目收尾按「收尾菜单」四步：全量测试 → 环境检查 → 给用户 3 选项（交付/继续/归档，带推荐）→ 执行+清理临时文件+决策写入 `research/DECISIONS.md`（项目内同名文件同理）+ 交接清单（怎么启动/部署/排查）。收尾先跑 `bash setup/supervisor-verify.sh` 全量（日常 `--fast`），输出作为 Gate 证据；上下文有风险或需换会话时按「交接单」流程写 `.dsh/handoff.md`。

## 反模式（不要做）

- **自己全干**：派发后又自己重写；你只做审查与整合。
- **命令缺上下文**：对 fresh 对话框说「按之前说的做」→ 跑偏/空转。
- **写范围重叠**：两个对话框同时改同一文件必冲突；开工前切分。
- **口头验收**：看到「已完成」就收工，不跑测试/看 diff。
- **等待空转**：反复轮询同一状态；应用 `wait_agent` 等变化。
- **范围漂移**：让对话框自定架构/范围；决策权留主管。
- **过度设计**：加用户没要的模块；先满足完成定义。
- **简单任务开一堆对话框**：协调成本+token（约 15×）超过并行收益；能单会话做完别拆。
- **没有终止条件**：只写「调研一下」不写查到什么程度停 → 无限检索/空转。
- **该检索却凭记忆**：外部事实（版本/项目现状/API 行为）不检索直接编，或无预算无核验地「查一下」。
- **擅自提权**：改审批/沙箱/权限预设，或让对话框越权写入、发布、删除；被拒后反复重试。
- **跳过计划直接派实现**：没有 plan/brief 的实现者只能靠猜，必跑偏/返工。
- **给评审 pre-judge**：告诉评审「这个不用报」= 门禁放水；评审须独立给结论。
- **无限返工/丢弃 blocking**：同一问题反复「再优化」无上限、blocking 静默丢弃；2 轮不收敛即升级裁决。
- **脏基线开工**：不查 `git status` 就动手，他人未提交改动会混进 diff、无法回退。

## 与用户沟通

- 结论先行，3–7 条要点，不贴大段日志。
- 需用户决策时：给选项+推荐+理由。
- 不擅自扩大授权范围；不可逆操作先问。
- 用户提供密钥/账号：给傻瓜操作（在项目 `.env` 里填，或放本机文件后你读），不要求贴聊天；需要素材时给清单。
