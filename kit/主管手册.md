# 项目主管 · 使用说明

一句话：**你只对主管说目标，主管拆解后在工作区里开多个对话框并行干活，最后统一验收交付。**

## 怎么用

1. **直接说目标**：在工作区里新建一个会话，把目标丢给主管（如「做一个 X 项目的官网，先搭骨架再加 3 个页面」）。AGENTS.md 会自动让这个会话以主管方式工作。你不需要特意说「使用 Agent Teams」——在本工作区把项目目标交给会话即视为授权；如果该会话没启用 Team 组合包，主管会降级为单会话执行并告诉你。
2. **显式进入主管模式**：说「你当项目主管」「把这个项目拆成并行任务，开几个对话框做」。
3. **看并行**：主管会建共享任务板 + 开多个研究/开发对话框。teammate 的会话**不在左侧对话列表**里（侧边栏会隐藏子代理来源的会话），要从**会话页头的「智能体团队」面板**进入：面板显示成员与任务板，点成员行可打开其完整子会话；面板本身只读。Teams 启用后如果面板没出现，刷新页面即可。
4. **干预**：直接对主管说「停掉 X」「让 Y 补一次测试」「先汇报进度」；主管负责转发或中断。
5. **收回控制权**：说「关掉所有对话框」「不要并行了，你自己做」。

## 在其他工作区快速建立主管

本工作区的 `setup/` 目录是一个**可移植安装包**，一条命令就能把主管建到任意工作区（安装包路径以本工作区实际位置为准）：

```bash
KIT=<解压后的 project-supervisor-kit 目录>

# 1) 最小安装：常驻规则 + 技能 + 本手册
bash "$KIT/install-supervisor.sh" /path/to/workspace

# 2) 顺带带上调研资料与决策模板（research/ 共 7 份）
bash "$KIT/install-supervisor.sh" /path/to/workspace --with-research --with-setup

# 3) 安装为全局技能：之后任意工作区说「你当项目主管」即可，不必每个工作区重装技能
bash "$KIT/install-supervisor.sh" /path/to/workspace --global-skill

# 目标目录已有 AGENTS.md 时默认不覆盖（生成 AGENTS.supervisor.md 供合并）；确认覆盖加 --force
```

- 原理：`AGENTS.md` 按会话 cwd 注入 → 该工作区每个新会话自动成为主管；`.dsh/skills/project-supervisor/SKILL.md` 提供详细流程；`--global-skill` 把技能装到 `~/.dsh/skills/`（所有工作区共用）。
- 建完后在 DSH 里把目标目录打开为工作区、新建会话（cwd 必须是该目录），直接说目标即可。
- 已实测：全新目录、已有 AGENTS.md（不覆盖）、`--with-research`、`--global-skill`、重复执行幂等，全部通过。
- **全局技能已安装**（2026-10-24）：`~/.dsh/skills/project-supervisor/SKILL.md`，任意工作区说「你当项目主管」即可触发；同名时项目级技能（`.dsh/skills/`）优先。升级时重跑安装脚本即可（旧文件会自动备份为 `.bak.<时间戳>`），卸载则删除该目录。

## 一键安装到新工作区（复制口令，最省事）

1. 打开「主管」面板 → 快捷动作 → **复制一键安装口令（新工作区）**（也可直接复制套件里的 `一键安装口令.md`）。
2. 到目标工作区**新建会话**，粘贴口令发送；agent 会从 GitHub 下载套件、用 `install-supervisor.sh`/`.mjs` 装进当前工作区，并逐项验收（AGENTS.md、技能、模板、手册、版本记录）。
3. 装完**在同一目录再新建会话**，常驻规则生效；原会话按 AGENTS.md 继续。

口令自带安全边界：默认只补缺失、不覆盖已有文件、不自动 git commit/push；目标工作区原有 README/DECISIONS 不受影响。套件版本以目标工作区 `.dsh/supervisor-kit.json` 为准。

## 工程化维护（维护者）

安装包目录（本工作区为 `setup/`）自带四个维护脚本（只在源工作区使用，不随分享包分发），改规则或文档后按顺序跑：

```bash
cd "$(dirname "$0")"   # 解压根目录
bash selftest.sh                # 一键回归：语法 + 4 组安装 + 幂等 + 安装器 dry-run/force/预检 + 补丁自测 + 打包校验（当前 18 项）
bash sync-kit.sh --check        # 检查源文件与模板副本是否漂移（有漂移打印 diff 并 exit 1）
bash sync-kit.sh                # 把源文件同步进模板副本（幂等）
bash sync-kit.sh --global       # 顺带更新 ~/.dsh 全局技能（旧文件自动备份 .bak.<时间戳>）
bash build-dist.sh              # 构建分享包：脱敏 → zip → sha256 → 内容抽查
bash verify-facts.sh            # 联网复检引用链接、GitHub 星数、DSH 常量（DSH 升级后跑）
```

> 维护脚本只在**源工作区**使用（它们读取工作区根的 `AGENTS.md`、`.dsh/skills/...`、`research/`），构建分享包时会自动剔除，避免把开发工具与脱敏规则一起发给朋友；朋友拿到分享包只需要 `install-supervisor.sh` / `install-supervisor.mjs`。

- 版本号在 `setup/VERSION`，变更记录在 `setup/CHANGELOG.md`；分享包与 `.sha256` 同目录，可直接 `shasum -a 256 -c` 校验。
- 注意：`sync-kit.sh --check` 只比对 10 个模板副本，**不检查** `~/.dsh` 全局技能与 `dist/` 分享包；改完源文件后必须跑 `sync-kit.sh --global` 和 `build-dist.sh`，否则新工作区/朋友拿到的是旧版。
- 本工作区已 git 化：`.gitignore` 忽略 `dist/`（产物可重建）与临时文件；改完先 `git status`、`git diff` 再提交。
- 一次典型改动顺序：改源文件 → `selftest.sh` → `sync-kit.sh` → `build-dist.sh` → `verify-facts.sh`。
- 改 `plugin/dsh-project-supervisor/` 后额外跑：`node --check plugin/dsh-project-supervisor/client.js` + `node plugin/dsh-project-supervisor/scripts/smoke.mjs`（selftest 已包含）；需要看真实界面时用 `scripts/e2e-screenshot.mjs`（见插件 README），改完刷新 DSH 页面。

## 主管会做什么

- **立项**：把目标变成完成定义、工作分解、依赖顺序、写范围。
- **派发**：每个独立工作流开一个对话框（fresh 上下文），命令自包含（目标/输入/约束/验收/边界/交付路径）。
- **信息缺口判断**：先分清「本工作区已有的事实」和「得去外面查的事实」：需要外部资料时，命令里会写明「上网/上 GitHub 查什么、查几次或多久、怎么核验来源、不得编造链接」；本仓库内部事实则直接指定先读哪些文件。
- **并行**：独立工作流直接并行，不必等你批准（同上面的常驻授权口径）；有依赖按 DAG 串行，用 `blocked_by` 控制。
- **监管**：等待、看任务板、抽查产物、纠正偏航、必要时中断重派。
- **验收**：跑测试/构建、看 diff、抽查文件、核对引用链接；不采信「已完成」的口头结论。
- **汇报**：结论先行 + 完成项（文件路径）+ 验证结果 + 风险 + 下一步。

## 给零基础用户：主管会自动帮你避开的坑

你不需要懂代码。主管会按这套规则主动兜底；你只要说清「想做什么」，并在花钱/发布/删除这类不可逆动作前做个决定。

如果你已经熟练、不想被新手引导打断：打开侧栏「主管」面板，在「工作方式」区第二张「工作开关」清单第 1 行的「零基础保护」，关掉行右侧的开关即可。状态写在 `<工作区>/.dsh/supervisor.config.json`，主管开工前会先读它；密钥、不可逆动作确认等安全底线仍会保留。

| 新手常犯错误 | 主管会怎么做 | 你可以怎么配合 |
|---|---|---|
| 不建 git、没有回滚点 | 开工先 `git init` + `.gitignore` + 首次提交，之后每步提交 | 不用管；改坏了直接说「回到上一版」 |
| 不选架构、技术栈乱 | 给 2–3 个方案并替你定一个最简的，写进 `DECISIONS.md` | 说「你定」即可；有偏好就说 |
| 一次想做太大 | 先做最小可运行版本（MVP），切成小步 | 先确认「第一版要能做什么」 |
| 不跑起来就加功能 | 每步先跑通/测试，贴命令与结果 | 帮忙点一下页面、看是否符合预期 |
| 密钥/密码写进代码 | 生成 `.env.example` 占位，让你在项目 `.env` 里自己填；提交前自动扫描 | 按主管步骤填进 `.env`，不要发聊天记录 |
| 不写 README，换会话就丢 | 建 `README.md`（目标/启动/依赖）和 `DECISIONS.md`；新会话先读回 `README`/`DECISIONS`/`git log` 再复述 | 新会话直接说「继续上次的项目」，主管会先复述目标与上一步，不会从头再问 |
| 报错不读、靠猜 | 先读报错定位文件与行，再修 | 把报错原文整段贴过来，别只说「坏了」 |
| 删库/发布/花钱不确认 | 列清动作、影响、可恢复性再等你确认 | 只对这些事做确认即可 |
| 不备份、只在本地 | 重要项目建远端私有仓库或定期导出备份（首次上传前问你） | 确认「可以上传到私有仓库」即可 |
| 成本/自动续费失控 | 优先免费额度，写清哪里会花钱，续费前问你 | 预算敏感就直接说「别花钱」 |
| 本地能跑、别人打不开 | 收尾给部署步骤和可访问地址 | 要给别人看时提前说 |

**新项目开工五件事**：git 仓库 + `.gitignore`、README（目标/启动/依赖）、架构选型记录、3 条可执行验收标准、安全默认（`.env`、不提交密钥），另外重要项目会加远端备份。

**你最少只需要做四件事**：① 说清目标和使用场景；② 确认第一版范围（主管会先问「第一版要能做什么」）；③ 按主管给的步骤提供必要材料（API key 等填入项目 `.env`，不要贴进聊天；没有就直说）；④ 项目跑起来后反馈（有界面就点一点；没界面就看主管贴的运行结果/截图），并对不可逆/花钱的事确认。

## 新项目需求追问（默认开）

你只要说「我想做一个 X」，主管会像产品经理一样**先追问需求再动手**：每轮 3–5 个问题、每题带默认答案（可只回「用默认」），直到它能写出 MVP、验收标准和主要约束、你连续两批只回「用默认」、或你说「够了 / 直接做 / 开始吧」，最多 3 批。追问完先给你一页纸摘要，写进**项目根目录**的 `README.md` 与 `DECISIONS.md`（不是本工作区的 `research/DECISIONS.md`）再开工。

- 只在「提出新项目」的那轮触发；接着旧项目改、修 bug、日常调整不会追问。
- 关闭：DSH「主管」面板 →「工作方式」区「工作开关」清单第 5 行的「新项目需求追问」开关（或 `.dsh/supervisor.config.json` 的 `"requirementInterview": false`，缺省按 `true`）；关闭后说「先问清需求」仍可临时执行。
- 依据：见 [research/07-requirement-interview.md](research/07-requirement-interview.md)（8 个开源仓库：spec-kit 的 5 问定额、superpowers 的一条一问 + HARD-GATE、BMAD 快慢双路径、vibe-check 零基础语气；6 个 MIT，2 个无许可证仅参考思路）。

## 提示词润色（默认开）

主管默认把你每条指令先「工程化」再执行：判断场景（对话请求 / 常驻规则 / 编码或调研任务 / 文档处理）→ 找出会挡路的缺口（目标、输入、约束、验收、交付、风险）→ 用最少技巧补成专业提示词（不改你的意图；缺的事实留 `[占位符]`，不编造）→ 用一行「润色要点」说明改了什么，然后立即执行。

- **开关位置**：DSH「主管」面板 →「工作方式」区「工作开关」清单第 4 行「提示词润色」行右侧开关（默认开），状态写到 `<工作区>/.dsh/supervisor.config.json` 的 `"promptPolish"`；主管开工前先读它。
- **关闭后**：直接按你的原话执行，仍会写明关键假设；随时可以再打开。也可在单次指令里说「这次别润色」。
- **技能本体**：`.dsh/skills/improving-prompts/SKILL.md`（完整《Improving prompts》流程；也可单独触发「帮我优化这个提示词」）。
- **为什么默认开**：多数人给的是「想法」不是「任务书」；补全目标/验收/交付能显著减少返工，代价只是一行说明。

## 派发模式：效率优先 / 严格派发（默认效率优先）

DSH「主管」面板「工作方式」区第一张「主管工作模式」卡片可以选择主管的工作形态，状态写 `<工作区>/.dsh/supervisor.config.json` 的 `"dispatchMode"`；主管开工先读它，切换立刻保存、只影响之后的新任务。

| 模式 | 谁写文件 | 适合 |
|---|---|---|
| **效率优先**（默认） | 紧耦合跨文件改动、浏览器/测试迭代、10 分钟内小修补由主管亲自做；独立新文件、调研、评审、文档包、可独立验收的模块派给对话框 | 日常：又快又稳 |
| **严格派发** | 所有文件写入都交给对话框（哪怕改一句话）；主管只拆解、登记、写命令、评审、验收、集成，不亲自 Edit/Write | 想验证「主管真的只指挥」、高风险或需要留痕的项目 |

- **怎么切换**：「工作方式」区第一张「主管工作模式」卡里的两个选项（效率优先 / 严格派发），点击即保存；改配置文件后新会话也会读到。
- **限制**：严格模式更慢、token 更多；若对话框额度/成员上限不够，主管会停下说明阻塞，不会偷偷自己写。
- **验收不变**：两种模式下主管都必须亲自跑测试、看 diff、按证据验收。

## 工作流硬化（v1.8.0，来自 superpowers 的 14 条）

学习对象是 MIT 的 [superpowers](https://github.com/obra/superpowers)（约 30 万★）。它证明有效的是**流程**，不是更长的 prompt；这 14 条已落成常驻规则、SKILL 章节与五个模板文件（4 个硬化模板 + wake-brief）：

| 能力 | 你会看到的变化 | 落点 |
|---|---|---|
| 计划即文件 | 大任务先写计划，每个对话框拿到一份 task brief；派发只引用文件路径，不再靠主管口述 | `templates/plan.md`、`templates/task-brief.md` |
| 两段式交付 | 每个写文件的对话框完成后，另开一个只读评审对话框，给「规格符合度 + 质量」双结论 | `templates/review-gate.md` |
| 完成声明 Gate | 说「完成」前必须附验证命令与输出；红旗词（should / probably / seems / 已经好了）会被打回 | SKILL「完成声明 Gate」 |
| 有界返工 | 同一问题最多 2 轮，每轮必须复审；不收敛就升级或交还你裁决 | SKILL「有界返工」 |
| 任务账本 | 每轮决定、阻塞、重派都记一行；换会话或上下文接近上限后能接着干 | `templates/ledger.md` |
| 小批量合并 | 同型小改跨文件时合并成一次派发，只审一个 diff | SKILL「小批量合并派发」 |
| 调试 Iron Law | 修 bug 先复现 + 找到根因，再改代码；3 次修不好就质疑架构 | SKILL「调试 Iron Law」 |
| 收尾菜单 | 收尾先跑全量测试，再给「合并 / PR / 保留」三个选项让你选 | SKILL「收尾菜单」 |

另四个工具：**红旗借口表**（防「这次太简单不用查」）、**技能压力测试**（新规则先用被诱导的 fresh 对话框验收）、**模型分级**（按复杂度建议，DSH 暂不支持 spawn 选模型）、**多平台适配清单**（DSH Web/CLI、Windows/macOS）。它们都在 SKILL 同名章节，不确定时让主管「按工作流硬化流程做」。

## 对话框与并行判据

- 这里的「对话框」= DSH 工作区里的一个独立会话；主管通过 Agent Teams 的 teammate 机制创建与指挥，每个 teammate 有独立上下文与独立会话，可在 Team 面板查看。
- 判断能否并行看三条：**写文件不重叠**、**无先后依赖**、**可独立验收**。三条同时满足才并行，否则串行。
- 同一文件同一时间只允许一个对话框写，避免互相覆盖。
- 默认并行 2–4 个；任务太碎不值得并行。

DSH「主管」面板「工作方式」区「工作开关」清单第 3 行的「模型协作」开关（默认关；开启时自动展开 auto/manual 两选项与 6 行路由表），打开后二选一：

| 选项 | 行为 |
|---|---|
| AI 自动选择（默认） | 打开后显示一张 6 行「自动路由表」，逐任务类型可编辑；「推荐默认」= 规划/架构、独立评审用更强的模型，实现编码、调研检索、文档整理、测试验证用更快的模型 |

- 状态写入工作区 `.dsh/supervisor.config.json` 的 `modelCollaboration`，只影响之后的新任务。

## 团队复用（v1.8.6）

成员是持久会话：优先唤醒已有 inactive 成员，而不是每次新开。派发顺序：

1. `list_agents` 对照 `.dsh/team-roster.md`（8 席位角色卡）→ 有匹配就 `send_message` 唤醒；
2. 唤醒消息带 **warm-start 简报**（模板 `.dsh/skills/project-supervisor/templates/wake-brief.md`）：当前 HEAD/规则版本/任务/唯一写范围/验收，要求先回 ≤120 字对齐摘要、主管确认后再动手；
3. 只有角色缺失、写范围冲突、需 fresh 上下文才 `spawn_teammate`；名额满不得 spawn（复用/串行/报阻塞）；
4. 只读/一次性/跨模型用 `subagent`（不占名额、可指定模型）；多轮/共享任务板用 teammate；简单任务不并行。

## 自动工作（无人值守，默认关）

一句话：**你离开电脑时，主管可以自己接着推进可完成的工作；所有要你拍板的事都攒着，回来一次性看。**

**怎么开**：在「主管」面板「工作方式」区第二张「工作开关」清单第 2 行打开「自动工作」开关（配置落 `.dsh/supervisor.config.json` 的 `"autoWork": true`），或者直接对主管说「开启自动工作」。默认是关的；关着时行为和以前完全一样（照常弹窗提问、正常派发、正常收尾）。**怎么关**：在面板关掉，或说「关掉自动工作」；自动工作跑完一轮也会自己置回关闭，并在总结里告诉你。

**更经济的自动化（默认关）**：「自动工作」开关行内还有一个缩进的次级开关「更经济的自动化」（配置字段 `"economicalAutoWork"`，默认 `false`；「自动工作」关闭时置灰、不可单独开启）。打开后自动工作只在 **DeepSeek 谷价时段**推进——北京时间周一至周五 **09:00–12:00、14:00–18:00**（UTC 周一至周五 01:00–04:00、06:00–10:00）之外的全部时间 + 周末/中国法定节假日全天为谷价（这两个工作时段是高峰；谷价约为峰价的 50%，来源 DeepSeek 官方价格页 2026-11-01 核实）。它只约束自动工作发起的模型调用，你手动聊天/派发不受影响；细则见下方「谷价闸门与暂停/续跑」。

**夜间它做什么**：
- 从队列 `.dsh/auto-work-queue.md`（模板 `.dsh/skills/project-supervisor/templates/auto-work-queue.md`）和任务板里挑能做的活，按 `schedule_create` 周期脉冲（建议 10–15 分钟一次）自唤醒续跑；
- 每轮先读队列、任务板与在跑对话框，只派发「待办、无前置依赖、写范围不冲突」的任务；
- 用只读脚本 `node .dsh/skills/project-supervisor/scripts/peek-mailbox.mjs` 查看**两类排队信息**：①你在界面「排队发送」但还没投递出去的用户消息（next-turn，当前轮读不到；脚本只读可见，无人值守时不自行注入）；②团队对话框之间未投递的消息。都不打断在跑的人；
- 你在场且想让它**立刻**读到排队消息：在输入框按 Cmd/Ctrl+Enter（或排队列表点「插话发送」），会在下一步边界投递、不打断当前动作；自动工作发现 `userPending > 0` 时会尽快收尾当前轮，让下一轮读这些消息；
- 缓存区五节固定：`## 排队任务` / `## 阻塞` / `## 待回答的问题` / `## 自动工作日志` / `## 经济模式状态`，条目以 `- ` 开头，空节写 `- （空）`。「经济模式状态」只在开启「更经济的自动化」时填写，九个字段：状态 / 边界（高峰起止，UTC+北京） / 暂停原因 / 当前任务与 phase / 最后检查点 / 产物路径 / 在跑 agent / 下一步 / 恢复时间；关闭时写 `- （空）`。

**夜间它不做什么**：
- **不弹窗问你**：本该问的问题写进「待回答的问题」，并按推荐的默认假设继续做，回复里说明；
- **不请求授权**：推送、发布、删除、花钱、改系统配置、对外发送这类不可逆动作一律不自动执行，只记进「阻塞」等你回来拍板；被拒绝过的动作不会重试；
- 不改你的立项范围与完成定义，也不偷偷绕过权限。

**什么时候会停**：你回来或发新消息；连续 2 轮没有进展；遇到必须不可逆动作；队列只剩阻塞；到了约定的时长/轮次上限。收尾时会：停掉脉冲 → 把 `autoWork` 置回 `false`（其他配置不动）→ 写「自动工作日志」→ 给你一段总结（完成 / 阻塞 / 待回答问题与默认假设 / 下一步）。

**谷价闸门与暂停/续跑（开启「更经济的自动化」后生效）**：
- **适用条件**：自动工作会发起的模型调用（主管默认模型、模型协作的 `autoRoutes`/`assignments`、继承给对话框的模型）只要包含 `deepseek-official/*` 就适用；全部显式非 DeepSeek 则不限制；无法判定时保守按适用处理。
- **每 tick 先判时段**：高峰开始前 **20 分钟**起只收尾，不启动新任务/子对话框/长等待；高峰开始后等当前 step 到检查点即暂停（最多再跑 **≤10 分钟**）；暂停期间零模型调用；谷价开始后由 tick 续跑（下一次 tick 定在谷价开始后 1–3 分钟）。
- **连续性**：暂停前把只在对话里的结论写盘（`.dsh/auto-work-queue.md` 的「经济模式状态」节 + LEDGER + 任务 brief）；恢复时先读该状态节、任务板与 `list_agents`，核对产物/任务状态——已完成不重派、从中断点继续；状态缺失时按队列 + LEDGER 重建（恢复幂等）。
- **节假日**：没有内置法定节假日日历，以你的告知/队列备注优先；无法判定时按「工作日高峰」保守处理（宁可少跑，不在高峰跑）。
- **边界**：只约束自动工作发起的调用；谷价闸门之外仍受原有停止条件（你回来 / 连续 2 tick 无进展 / 不可逆动作 / 到达上限）约束。

**早上先看什么**：① `.dsh/auto-work-queue.md` 的「阻塞」和「待回答的问题」（这是要你拍板的清单）；② 主管给的总结；③ `.dsh/auto-work-queue.md` 的「自动工作日志」（它做了什么、为什么停）。

**限制与前提**：P0 只落地规则与队列，不弹窗靠规则约束；「到点自动把提问变成限时等待」是 **P1 的可选补丁 `auto-work-timed-ask`**（未应用时不生效），「自动工作权限预设」同为可选补丁。自动工作不改变对话框权限，也不保证任务一定能做完——只保证不阻塞、不越权、留痕可查。注意「排队发送」的用户消息默认排到**下一轮**才投递；想当前轮立即处理，需你手动用「插话发送」（Cmd/Ctrl+Enter）。

## 效率工具：体检、一键验收与交接

一句话：**开工/收尾先体检，交付前后一键验收，怕断上下文就写交接单——三条命令都只读，不写你的项目文件。**

**① 环境体检**（用在新会话开工、接管项目、遇到「消息没反应/工具报错/上下文异常」、收尾前）：

```bash
bash setup/supervisor-doctor.sh          # 人类可读表：PASS/WARN/FAIL + 汇总行
bash setup/supervisor-doctor.sh --json   # 给程序/面板读
```

看末行 `汇总: PASS n / WARN n / FAIL n / SKIP n`：**FAIL 必须先处置再开工**（典型：AGENTS/SKILL 超预算、套件镜像不同步、插件语法/加载错误等）；其余 WARN（脏基线/可选依赖/残留备份）记一笔即可。

**② 一键验收**（用在每批交付收尾、独立评审之前）：

```bash
bash setup/supervisor-verify.sh --fast   # 日常快速
bash setup/supervisor-verify.sh          # 收尾/发布全量
```

按序跑体检、套件同步、事实复检、插件测试、脚本自测、全量回归、git 卫生/密钥扫描；单步失败会继续跑完并最终返回非 0。完整输出就是 Gate 证据，评审可直接复用，不用重复跑。

**③ 交接单**（用在会话明显变长/提示上下文将满、要换对话框继续、你要离开电脑、担心会话中断；触发口径与 `AGENTS.md`/SKILL 一致：**>1200 条消息或会话日志 >4MiB**）：

主管会写 `.dsh/handoff.md`（模板 `.dsh/skills/project-supervisor/templates/handoff.md`），用 `spawn_teammate(context="fresh")` 开新对话框并把 handoff 当初始任务，同时把未完成任务在任务板 reassign 给它；原会话只留协调/验收/收尾。**交接只用 fresh + 文件，不用 fork 顶替**（fork 不减少上下文）。

**你回来后怎么验证交接成功**：① `.dsh/handoff.md` 各节填满（目标/完成定义/当前状态/已完成证据/未完成+命令/阻塞/权限预算/开工指令）；② 新对话框能复述目标与下一步，且任务板里任务 owner 已换成它；③ 旧会话不再改文件；④ 它跑过 `bash setup/supervisor-doctor.sh` 且无 FAIL。

> 两个脚本随套件 `setup/` 分发；没装套件的旧工作区可让主管按本手册临时执行等价检查，或先跑安装器。规则细节见 `AGENTS.md` 与 SKILL「效率工具：体检 / 一键验收 / 交接单」。

## 设计依据（调研结论怎么落到规则里）

| 规则 | 依据（详见 research/README.md） |
|---|---|

| 人类 gate 最小化 | DevSupervisor 审批 gate、VibeCtl plan 审批（01）：只在取舍/花钱/不可逆操作时打断 |

**分区级折叠**（插件 1.0.0）：5 个折叠按钮分别对应 `[data-zone="work-modes"|"runtime"|"checks"|"actions"]` 与「使用说明」；默认展开工作方式、快捷动作，收起运行状态、规则自检、使用说明；收起时标题行只留一行灰色摘要（运行状态「成员 n · 任务 n · 待投递 n」、规则自检「n / 9 项就绪」、快捷动作「7 个快捷动作」、使用说明「主管四步流程」、工作方式收起时「2 张设置卡」）；状态存 `localStorage["psup.zone.<zone>"]`（'1' 收起 / '0' 展开，刷新页面保持，与行级 `psup.collapsed.<field>` 互不影响）。默认收起态整页高 **1196px**（见下方「已实测」）：首屏（innerHeight 813）仍完整可见工作方式区 5 行开关（lastSwitchRowBottom=770 ≤ 813），运行状态标题行 top=806 仍在首屏；全部展开约 1500px（离线 harness 1498px）。

**五个开关**（在「工作开关」清单卡里逐行显示，每行右侧一个开关、行尾「说明」展开该行完整指引；折叠状态存浏览器 localStorage，默认收起；状态写到 `<工作区>/.dsh/supervisor.config.json`）：

- `"beginnerGuard": true|false`（清单第 1 行，默认 true）：关掉后主管跳过主动新手引导，安全底线仍保留。
- `"autoWork": true|false`（第 2 行，**默认 false**，见「自动工作」一节）：无人值守自动工作总开关。其行内下方有缩进次级开关「更经济的自动化」`"economicalAutoWork": true|false`（默认 false；`autoWork` 关闭时置灰，开启后只在 DeepSeek 谷价时段推进，见「自动工作 → 谷价闸门」）。
- `"modelCollaboration": true|false`（第 3 行，默认 false，见「模型协作」一节）：打开后二选一——「AI 自动选择」（默认）/「用户手动选择」。
- `"promptPolish": true|false`（第 4 行，默认 true，旧配置无该字段按 true）：关掉后主管直接按原话执行、不再先润色（仍写明关键假设）。
- `"requirementInterview": true|false`（第 5 行，默认 true）：关掉后新项目不再自动追问需求；说「先问清需求」仍可临时执行。

另有**工作模式**（不是开关，是二选一）：`"dispatchMode"` 为 `efficiency`（默认）或 `strict`，在「工作方式」区第一张「主管工作模式」卡里选择，决定主管自己写文件还是把每次写入派给对话框。

```json
{ "beginnerGuard": false, "promptPolish": true, "requirementInterview": true, "autoWork": false, "economicalAutoWork": false, "modelCollaboration": false, "dispatchMode": "efficiency", "updatedAt": "2026-11-01T00:00:00.000Z", "source": "dsh-project-supervisor" }
```

写入走插件 host 半侧的 `GET/POST /plugins/dsh-project-supervisor/config`（同源校验、路径必须在 `$HOME` 下、原子写、一次可只改一个字段）；host 半侧代码需要**重启 `dsh web`** 才加载，重启前点开关会先存浏览器 localStorage 并提示「重启 DSH 后请再点一次开关」（加载时只读服务端文件，不会自动回写 localStorage，所以重启后需要重新点一次才落盘）。只改 client 半侧则刷新页面即可生效。

```bash
bash plugin/dsh-project-supervisor/install-plugin.sh              # 装进默认 web profile（改动前自动备份）
bash plugin/dsh-project-supervisor/install-plugin.sh --uninstall  # 卸载
```

安装后**刷新 DSH 页面**生效。

## 下次新会话的冒烟清单

换一个新会话只发一句目标（如「做一个 X 项目」），30 秒内应看到：

1. 主管先给出完成定义 + 拆解 + 并行/串行判断，而不是直接开写；
2. 需要并行时先 `team_task_create` 再 `spawn_teammate`，任务板出现工作项；
3. 会话页头出现「智能体团队」面板，能点进每个对话框；
4. 主管不包揽实现，只做决策、审查、综合。

若没触发：确认新会话的 cwd 是本工作区（AGENTS.md 按 cwd 注入），或直接说「你当项目主管」。

## 已知限制（按 DSH 0.2.0-rc.2 实测）

- **fresh 上下文**：对话框不继承主管记忆，所有背景必须写进命令，否则它只能自己猜。
- **消息不重发**：`send_message` 返回 `accepted` 或 `queued` 都算发送成功且已持久化，重复发送会造成重复任务；`inactive` 只表示「没有轮次在执行」，不代表完成或失败。
- **写范围不设锁**：`write_scopes` 只是重叠提示，不会阻止写入；Bash、格式化工具、代码生成还能绕过文件版本校验，所以主管必须亲自看 diff、跑测试。
- **单进程共享 checkout**：没有 worktree、文件锁、merge；不要让多个 DSH 进程并发操作同一团队。
- **成员上限**：由 profile 组合包配置——包默认 **16**；可用 profile 的 patch 层覆盖（本机已设为 **16**，**重启 dsh web 后生效**，重启前以旧配置为准）。且**含失败成员、只增不减**、没有删除 API；`maxTasks=256` 个活动任务、每成员待处理消息 64 条、单条消息 64KB；`wait_agent` 等待区间 10 秒–1 小时。
- **“超时”是等待窗口，不是失败**：子智能体/队友没有墙钟超时；`wait_agent` 返回超时只表示窗口内没有变化。长任务拆 2–3 个阶段验收；超时后重新 list 继续，不重发消息、不重复派发。
- **切换选项的生效范围**：每个新任务/派发前重读配置；切换只影响之后的新任务，**进行中的任务保持开工时的选择**；开工时把当时选项记一行进 `DECISIONS.md`（便于审计）。
- **owner 不自动释放**：对话框失败、被中断或退出，都不会自动释放任务 owner。对主管说「把 X 的任务收回重派」，主管会用 `team_task_update` 的 reassign/reopen 处理。
- **扁平团队**：只能由 Lead 直接建成员；不支持嵌套团队、改名、删除、名字复用。
- 并行会增加 token 与时间成本；任务本身很小时，主管会直接做而不是开对话框。
- **模型自带知识会过期**：涉及最新版本、项目/GitHub 现状、API 变更时，主管应要求在命令里写检索与核验，而不是凭记忆直接做。
- **主管不能给对话框单独授权**：新对话框创建时继承固定的权限范围，审批策略固定为 `never`（需要审批的动作自动拒绝、内部无法提权）；`write_scopes` 只是提示不是锁。要硬隔离请在会话级用 `/permission` 选择权限预设，或把高风险操作留给用户手动执行。（已装 `team-permissions` 可选补丁后，沙箱范围可按对话框指定；审批仍固定 `never`，见「进阶」一节。）
- 主管不是万能的：验收看的是可执行证据，无法替代你对产品目标的判断。
- **Windows 兼容性（插件）**：本机 macOS 无法复现真机 Windows，已用 win32 路径语义模拟与崩溃安全测试覆盖（`compat-check` 32 项）；安装用 Node 脚本（`node install-plugin.mjs` / `node install-supervisor.mjs`），不需要 bash。若朋友反馈 DSH 起不来：先 `node install-plugin.mjs --uninstall` 再重启，仍不行删 profile `package.json` 的 `dsh-project-supervisor` 两处条目（详见《朋友测试指南》第 8 节）。
- **插件写配置的范围**：只允许把 `.dsh/supervisor.config.json` 写进用户 home 目录下的工作区；放在其他盘符（如 `D:\`）的工作区会拒绝写盘，面板开关退化为浏览器 localStorage 记忆（规则本身不受影响）。

- **单会话降级时**：会话未启用 Team 组合包时主管既执行又自检，「写者不给自己签收」只能降级为自检并在汇报中说明。

## 进阶（可选）：给单个对话框指定权限范围

原生 DSH 无法为单个对话框设置权限（子会话权限在创建时固定、审批固定 `never`）。工作区里带了一个 opt-in 补丁，让主管派发时可按任务风险选择新对话框的沙箱范围：

| `sandbox` | 适用 | 效果 |
|---|---|---|
| `read-only` | 调研、评审、检查 | 写文件与写盘命令被沙箱拒绝 |
| `workspace-write` | 实现、改文件 | 只能写当前工作区（推荐默认） |
| `danger-full-access` | 仅用户明确要求 | 不限制（慎用） |

补丁 v2 还支持 `tools` 收窄**可见工具**：传 `tools: "read-only"` 时，子对话框只保留读/检索/汇报类工具（read、grep、glob、skill、todo_write、web_search、web_fetch），不能写文件、不能跑 bash；不传则与原生一致。建议调研/评审同时传 `sandbox: "read-only"` + `tools: "read-only"`——**写保护靠 sandbox，tools 只是收窄可见工具**，两者不是同一层。

补丁在 `patches/team-permissions/`（说明见该目录 README），本机当前状态可查：

```bash
python3 patches/team-permissions/patch.py status   # PATCHED / unpatched
python3 patches/team-permissions/patch.py selftest # 不改安装，只在临时副本自测
python3 patches/team-permissions/patch.py apply    # 应用（自动备份到 ~/.dsh/patches/...）
python3 patches/team-permissions/patch.py revert   # 回滚
```

- **应用后必须完整重启 DSH 才生效**（模块只在启动时加载，刷新页面不算）。
- 补丁版本 v2：`status` 会显示已应用版本；旧 v1 升级方式是先 `revert` 再 `apply`（两步连续执行，中间不要重启 DSH）。
- DSH 版本不是 `0.2.0-rc.2` 时 `apply` 默认拒绝，需 `--force`（DSH 升级后先看 `status`，再决定是否重打）。
- 审批策略仍是 `never`：补丁只改沙箱与工具可见性，需要人工批准的动作用户自己决定。
- DSH 升级或 npx 缓存重建后补丁会丢失，`status` 显示 unpatched 时重跑 `apply` 即可。
- 未装补丁时主管不会传 `sandbox`/`tools`，行为与原生一致。
